# 重启 RestArtEngine DevLog：知乎连载写作规范

> 栏目：知乎「重启 RestArtEngine DevLog」（头图字样：开发手记 / ENGINE DEVLOG）
> 版本：v1.14（2026-10-29）
> 配套底稿：[ZhihuSeriesLedger.md](ZhihuSeriesLedger.md)
> Codex 入口：项目技能 [`.agents/skills/restarengine-devlog/SKILL.md`](../../.agents/skills/restarengine-devlog/SKILL.md)，由仓库根目录 `AGENTS.md` 触发

## 0. 这套规矩解决什么

本规范当前位于独立协作库 `local/docs/`。公开 `docs/` 不承载写作、协作、进度或这些流程的管理规则；公开根 `AGENTS.md` 只指向协作 [AgentEntry.md](AgentEntry.md)。正式稿输出根以本机忽略文件 `local/machine/Paths.md` 为准，此次同步整理不移动已完成稿件。

资料位置和传输边界见 [LocalDevelopmentGuide.md](LocalDevelopmentGuide.md)，双仓库流程见 [WorkspaceSync.md](WorkspaceSync.md)。本规范、底稿、变化审计与写作技能只能进入独立协作库；正式文章和媒体在仓库外。文中“仓库里的文件”如指写作过程记录，是协作库资料，必须检查是否已提交和推送；公开引擎 clone 不恢复它们。机器输出路径不进入任一Git仓库。

这个系列写的是「一个技术美术和 AI 一起，把 RestArtEngine 从零做出来」。

它不是按天记的流水账，也不是「三个故事」式的开发随笔。每期按系统/模块讲清楚这一版做了什么：结构、渲染、操作、工程，各自改了什么，为什么改，怎么验证。底稿不单独成篇，它就是正文的骨架；读者看到的是一篇完整的技术文章，不是「正文 + 变更清单」。

但有一件事得先解决：我们怎么知道「上次之后」发生了什么。靠记忆不靠谱，靠聊天记录更不靠谱。Codex 每次会话都是新的，DeepSeek 只是这次会话里干活的模型，它不会记得上次聊了什么。能留下来的只有仓库里的文件。

所以这套规矩分三块：

1. 怎么切阶段。
2. 怎么把变化拆成正文的骨架。
3. 怎么把它写成人话。

最后还有一块：怎么把它交给 Codex，让下一次会话不用从头解释。

如果只记三句话：

> 一期只讲一个阶段；底稿融进正文；每个结论都要有截图、源码或公式撑着。

第一次用，按这个顺序：

1. 第 2.4 节，确认输出位置和这一期的日期。
2. 第 2 节，定这一期从哪到哪。
3. 第 3 节，把变化拆成正文的小节。
4. 第 4、5、6 节，写正文，补截图、源码和公式。
5. 第 8 节，发布前检查。
6. 第 9 节，交给 Codex。

## 1. 读者和底线

### 1.1 写给谁

- 玩过引擎、写过 Shader、用过 UE 或 Unity 的技术美术。
- 想自己做个渲染 demo，但不知道从哪下手的独立开发者。
- 对「AI 到底能不能写引擎」好奇，但听腻了发布会话术的人。

不要求读者懂 C++ 模板、COM 或 D3D11 的细节。出现这些词时，用一句人话解释，再往下写。

### 1.2 四条底线

1. **只写跑过的东西。** 代码写了但没跑，就说「代码里有了，还没实测」。
2. **计划就是计划。** 「下一步打算」不能写成「我们已经」。
3. **边界要写清楚。** 没做完的、有限制的、没验证的，都要说明；不用编故事，也不用「后续优化」糊弄。
4. **不泄露。** token、网关地址、内网 URL、本机绝对路径、别人的聊天记录，都不进正文和截图。

第 4 条不是小事。这个仓库的截图里，特别容易带出这些东西：

- `AGENTS.md` 里的 `base_url` 和 `experimental_bearer_token`。
- `E:\...\RAEngine\...` 这样的本机绝对路径。
- `C:\Users\<用户名>\...`、终端里的环境变量、API key。
- `%LOCALAPPDATA%\RAEngine\engines.json` 里的本机引擎列表。

发布前把截图放大，边缘和终端窗口都看一遍。

### 1.3 固定头与称呼

每期开头用同一个头，不要每期换格式：

```text
Section NN｜YYYY-MM-DD

RestArtEngine vX.Y.Z

Commit：from <start> to <end>

<repo URL>
```

- 工程名只写 **RestArtEngine**：一个词，R/A/E 大写。不要写 RestartEngine、RestartEngin、RAEngine。
- `RAEngine` 只出现在文件格式、命名空间、目录名（`RAEngine.Project`、`rae`、`%LOCALAPPDATA%\RAEngine`），不在正文里当工程名。
- 对外标题固定为 `重启 RestArtEngine DevLog NN｜<短主题>`。主题可以用中文或英文：DevLog01 用 `Engine Initialization`，DevLog02 用 `创建可编辑的引擎工作空间`；同一期只选一种，在底稿记录。
- DeepSeek 写「补充模型」，不写「后端模型」；provider 写「自定义 model provider」。
- 头里的 commit 用短 hash；正文需要时再给全 hash。
- 头里不放 token、网关、内网地址。

## 2. 一期怎么切

### 2.1 一期不是一个星期

也不是一组 commit。一期是「一个能讲清楚的变化」。

判断能不能成篇，看三条：

1. 有一个读者能感知的新东西：画面、操作、工程流程，都算。
2. 有一次真实的验证：截图、日志、能复现的步骤。
3. 有一个取舍或限制：为什么这样做，为什么不那样做。

三条缺一条，就先别发。只有修 bug、改名字、升级依赖，不单独成篇，合并到下一期的一节里。

### 2.2 阶段卡

每期开头填一张卡。它不直接发布，但正文开头会用两三句话交代这些信息。

```text
期号：
标题：
状态：planned / drafting / published
发布时间：
文章日期：文件名里的日期，通常等于发布日
文章文件：开发日记/YYYY-MM-DD_第NN期_短标题.md
覆盖时间：上一期发布后 ~ 这一期发布前
起点：commit + 版本
终点：commit + 版本
验证：跑了什么命令，结果是什么
主线：一句话
主要小节：
边界：
下一期：
```

这张卡的内容最终要融进正文：期号、日期、版本、commit 范围放开头；主要小节变成正文标题；边界写在对应技术模块末尾。不要原样贴一张表上去。

「起点」是上一期文章开头写的终点 commit，也就是上一期实际讲到的最后一个 commit；不是上一期开始写的 commit，也不是发布那一刻的 HEAD。这一点很容易搞错，导致两期之间漏掉或重复。

「终点」是这一期发布时的 commit。如果发布时工作区还有没提交的修改，先在底稿里记下改了哪些文件，或者干脆提交完再发。不要让「文章里写了、仓库里找不到」。

### 2.3 打 tag

每期发布后，给仓库打一个 tag：`DevLog01`、`DevLog02`。

下次采集变化就很简单：

```powershell
git log --oneline DevLog01..HEAD
```

tag 比 commit hash 好记，也比「上个月那版」可靠。如果历史被改写过，tag 被移动了，以上一期文章开头写的 commit 范围为准。

### 2.4 输出位置、日期和 commit 的对应

#### 输出位置

连载正文不写在引擎仓库里，写在同步盘的固定栏目目录：

```text
<同步盘根>/TuringTechLab/运营内容/内容/知乎-RestArtEngine/开发日记/
```

这台机器的绝对路径记在 `local/machine/Paths.md`，该目录被协作库忽略。这份规范只写逻辑路径；公开 `AGENTS.md` 不保存私人路径。

| 部分 | 值 |
| --- | --- |
| 同步盘根 | 每台机器不同，以 `local/machine/Paths.md` 为准 |
| 栏目相对路径 | `TuringTechLab\运营内容\内容\知乎-RestArtEngine\开发日记` |

换一台机器，百度同步盘的挂载位置可能不同：`D:\BaiduSync\...`、`C:\Users\<用户名>\BaiduSyncdisk\...` 都有可能。所以：

- 换机器后，先问图灵老师：「这台机器的同步盘根在哪？」确认了再写。
- 确认前不要凭记忆新建目录。找错地方，文章会写丢。
- 根 `AGENTS.md` 是公开通用入口；不要复制另一机器的 `local/machine/Paths.md` 作为当前机器配置。
- 判断找对没有：目标目录里应该有 `head.png` 和 `head.psd`。没有这两个文件，就是走错了。
- 这个目录在引擎仓库外。当前会话如果只能写仓库，先说明写不进去，让图灵老师开权限；不要把正文改写到仓库里凑数。

这个连载是图灵老师指定的连续栏目，不走一次性的 `TECH-MEDIA-YYYYMMDD-NNN` 批次。不要为了“目录规范”把它挪进批次文件夹；要进正式批次，另建批次，连载目录保持不动。

目录结构建议：

```text
开发日记/
├─ head.png                 # 系列头图，别改
├─ head.psd                 # 头图源文件，别改
├─ 2026-10-20_第01期_短标题.md
└─ 2026-10-20_第01期_assets/
   ├─ 01-overview.png
   └─ 02-compare.png
```

正文和配图分开放。配图文件夹用同一日期前缀，找的时候不会串期。

#### 日期怎么标

文件名至少以 `YYYY-MM-DD` 开头；建议后面跟期号和短标题：

```text
2026-10-20_第01期_先让它能跑.md
```

- 日期用**发布日**，不是写作日。提前写好的稿子，先填计划发布日；实际发布日变了，改名，并在底稿里记一笔。
- 同一天发两篇，用期号区分：`2026-10-20_第01期_...`、`2026-10-20_第02期_...`。
- 写作源文件用 `.md`。如果另外导出 `.docx` 或 PDF，文件名也带同一日期前缀，但底稿只认 `.md`。
- 只有以 `YYYY-MM-DD` 开头的 `.md` 才算文章。`head.png`、`head.psd`、临时文件都不算。
- 不要用 `10.20`、`20261020`、`最终版`、`new` 这种排序会乱的写法。日期格式统一，机器和人才能按同一顺序读。
- 文件名里不要有 `: * ? " < > |`，Windows 上会出错。

#### 怎么判断「上次」和「今天」

按文件名排序，不按修改时间：

1. 列出目录里所有 `^\d{4}-\d{2}-\d{2}.*\.md$` 的文件。
2. 按文件名倒序排。
3. 最上面那个日期，就是上一次发布的文章。
4. 如果它的日期等于今天，说明今天这篇已经写了或发了；先问一句：是改这篇，还是再写一篇？不要直接覆盖。
5. 如果它的日期早于今天，那它就是「上次」，今天要写的是新的一期。
6. 如果目录里一篇文章都没有，这是第 1 期。

```powershell
Get-ChildItem -LiteralPath '<输出根>' -Filter '*.md' |
  Where-Object { $_.Name -match '^\d{4}-\d{2}-\d{2}' } |
  Sort-Object Name -Descending
```

修改时间只能当辅助：同步盘会改文件时间，复制、改名、云同步都会动它。日期以文件名为准。

#### 日期怎么对应到 commit

文章日期只是边界，commit 才是事实。顺序是：

1. 先看上一期文章开头写的「终点 commit」。有，就用它，别用日期猜。
2. 文章没写，或者这是第 1 期，才用日期兜底。
3. 第 1 期没有「上一期」，起点用仓库的第一个 commit（或者空仓库），不是「今天之前最后一个 commit」。否则前几天的活会全被漏掉：

    ```powershell
    git rev-list --max-parents=0 HEAD
    ```

    第 1 期没有父提交，收集时用 `git log --root <终点>`；写成 `8d80547..<终点>` 会漏掉初始提交。

4. 后续期数，用上一期文章日期的当天 23:59:59 作为上界，找这之前最后一个 commit：

    ```powershell
    git log -1 --before="2026-10-19 23:59:59" --format="%H %cd %s" --date=iso-strict
    ```

5. 找不到当天或之前的 commit，就继续往前找，直到找到为止。
6. 这一期的范围就是 `<上一期终点>..<这一期终点>`；第 1 期没有「上一期终点」，改用 `git log --root <这一期终点>`。终点取发布时最后一个引擎提交，写作规范、底稿、发布记录这类提交不算。发布前有未提交修改，先 `git status --short` 记下来。

同一天发两篇时，日期分不出先后，必须用上一期文章开头写的终点 commit 当起点。

日期兜底有一个前提：上一期发布时，仓库里的活已经提交到那天为止。如果上一期是「先发文章、后补提交」，日期会偏。遇到这种情况，以上一期文章开头为准，并在底稿里写清楚「文章日期」和「实际覆盖 commit」为什么不一致。

按本地日期算（这台机器是 Asia/Shanghai），不按 UTC。跨零点写的稿子，文件名用发布那天的日期。

### 2.5 正文不进 git

知乎正文、配图、导出稿不进 git。自 `8d64456` 起，本机写作规范、底稿和 DevLog skill 也由 `.gitignore` 忽略；可公开的引擎行为写入 `docs/` 技术说明；`local/docs/DevelopmentChanges-DevLog02.md` 等开发审计只保留本地。不要用强制添加绕过这项归属。

- 正式正文在百度同步盘，不在仓库。
- 仓库内只放临时副本，必须带 `.zhihu` 标签：
  - `.zhihu/`：草稿、导出、配图 staging；
  - `*.zhihu.md`：单篇草稿；
  - `*.zhihu.png` / `*.zhihu.jpg`：配图。
- `.gitignore` 通过忽略 `local/`、`artifacts/` 及不区分大小写的 DevLog/Zhihu 名称匹配保护这些本地资料；具体以当前规则和 `git check-ignore` 为准。
- 提交前跑：

```powershell
git status --short
git ls-files | Select-String 'zhihu|知乎|DevLog|\.zhihu'
git check-ignore -v .zhihu/example.zhihu.md
```

这条宽匹配用于检查遗漏；全部开发审计、过程记录、AI技能与写作资料均只保留本地，不因为可复用就允许提交。发现误跟踪时保留本地副本并按本地RepositoryPolicy处理，不用 `git add -f`。

- `local/docs/ZhihuSeries.md`、`local/docs/ZhihuSeriesLedger.md` 和 `.agents/skills/restarengine-devlog/` 是本机流程文件，当前不随仓库分发；正文和配图仍在外部目录。跨机器技术事实从公开领域说明恢复；本地开发/写作记录需要单独协作迁移。

## 3. 底稿：把变化拆成正文的骨架

### 3.1 为什么还要底稿

Codex 每次会话都是新的上下文。DeepSeek 只是这次会话里调用的模型，它不会记得上次说过什么。聊天记录不会自动变成下一次的输入。

能留下来的只有仓库里的文件。底稿就是这个文件，但它不是第二篇文章，也不发布；它只负责在下笔前把变化列全，然后被拆进正文。

底稿不是发布物，但每期都要先更新它。它是跨会话的事实状态和证据索引，写正文时再把内容融进去；不能用聊天记忆替代。

它不是给别人看的报表，是给下一次会话的自己看的备忘录。

### 3.2 一条底稿长什么样

底稿在 [ZhihuSeriesLedger.md](ZhihuSeriesLedger.md)。每条记录包含：

| 字段 | 写什么 |
| --- | --- |
| ID | 稳定编号，比如 `S-03`、`R-02` |
| 分类 | 结构 / 思路 / 渲染 / 操作 / 工程 / 稳定 / 修复 / 边界 |
| 变化 | 一句话，不超过 40 字 |
| 正文落点 | 放进正文哪一节；用截图、代码还是公式证明 |
| 证据 | 文件路径、命令、截图、日志 |
| 等级 | A / B / C |
| 期号 | 写进第几期，没写就空着 |

「变化」是技术事实，「正文落点」是文章结构。一条变化如果没有落点，就别硬写；留在底稿里，等下一期。

一条变化如果只有「代码更优雅」，读者感知不到，就别单独成段。可以合并到相邻小节，或者干脆不写。文章不是 changelog。

### 3.3 八个分类

| 分类 | 记什么 | 例子 |
| --- | --- | --- |
| 结构 | 东西放在哪、怎么连起来 | 把编辑器从入口文件拆成 SceneEditor / ViewportInteraction |
| 思路 | 为什么这样选、放弃了什么 | 前向和延迟共用 `ShadeSurface()`，而不是各写一套 |
| 渲染 | 画面里看得见的变化 | 新增 PCSS 软阴影、GTAO、解析光追 |
| 操作 | 手上能感知的变化 | W/E/R 切工具、F 聚焦、材质草稿 Apply |
| 工程 | 构建、发布、版本、跨机器 | 引擎身份、注册表、相对路径 |
| 稳定 | 崩溃、闪烁、加载、帧率 | Shader 编译失败保留上一版 |
| 修复 | 之前坏了现在好了 | 加载界面进度条位置偏了 |
| 边界 | 明确没做、暂时不做 | 没有 DXR、没有 Undo/Redo |

「结构」和「思路」最容易混。结构是「东西放在哪」，思路是「为什么放这」。一个讲结果，一个讲判断。文章里两者都需要，但别写成同一段。

「边界」不是免责声明。写清楚「这次没做」，读者才不会在评论里问「为什么没有 XXX」。如果已经决定以后也不做，就写「不打算做」，并给理由。

「稳定」不只记崩溃。加载时间、帧率、操作手感、重复劳动的减少，都是优化，都放这一类。一条优化如果有前后数字，优先写数字。

### 3.4 证据等级

| 等级 | 含义 | 能怎么写 |
| --- | --- | --- |
| A | 这轮跑过，有截图/日志/命令输出 | 「现在可以……」 |
| B | 代码和文档都在，但这轮没跑 | 「代码里已经有了，还没实测」 |
| C | 计划、设想、别人的经验 | 只能放「下一步」，不能写成「我们做了」 |

这条规矩是为了对付 AI 最容易犯的错：把「我知道这个功能存在」当成「我验证过这个功能能跑」。

写之前，把要用的条目从 B 升到 A。升不上去的，就老实写 B。

### 3.5 怎么采

先跑四条命令：

```powershell
git status --short
git log --oneline <起点>..HEAD
git diff --stat <起点>..HEAD
git diff <起点>..HEAD -- README.md docs/
```

第 1 期把 `git log` 换成 `git log --oneline --root HEAD`，否则漏掉初始提交。后面的 diff 看当前文件和 `docs/` 就够，不必强求从空树开始。

然后按这个顺序读：

1. **输出文件夹。** 最新一篇文章的日期是这次的时间边界；文件名和日期规则见 2.4。
2. **协作记录。** 这期的任务说明、用了哪些 `AGENTS.md`/`docs/`/skills/agents、哪一轮返工、准备固化什么。后面写第 0 节用。
3. **提交标题。** 先看一遍，但别直接抄。commit 是写给自己的，文章是写给读者的。一个 `update loading slide`，背后可能是「进度条终于按图片比例定位，换图不用改代码」。
4. **README 和 docs 的 diff。** 文档里新加的那句话，往往就是「读者能感知」的现成素材。
5. **代码里的关键结构。** 不用逐行读。看头文件、看目录、看新增的枚举和常量。
6. **验证。** 能跑就跑；跑不了就标 B，别猜。
7. **截图/录屏。** 记下窗口尺寸、相机、曝光、渲染路径。下次拍对比图要用同一套参数。

如果这期跨了很多提交，先按主题合并，再按「读者能感知」排序。不要按 commit 顺序写，那是流水账。

写作规范、底稿、发布记录这类提交，不算「引擎进展」。区间末尾如果只有这些提交，终点停在最后一个引擎提交。

### 3.6 从底稿到正文

底稿不是正文的附录，是正文的草图。每条底稿最后要变成正文里的一节，而不是一条清单。

- 一条底稿 = 一个小节，或一个小节里的一段。撑不起一节的，就和相邻条目合并，或者删掉。
- 先写一句判断：这次把什么从 A 改成 B，为什么。再给证据：截图、源码、公式、命令。最后写边界：哪里还没做好。
- 不要把底稿的表格、ID、等级贴进正文。读者不需要看到「R-02，等级 B」。
- 正文的顺序是：现状 → 改动 → 证据 → 限制。不是「变更列表」。
- 正文写完后，底稿只留日期、commit、落点，作为下一期的索引。
- 协作方法不是底稿里的一条，单独写；它的原料是 3.5 第 2 步的协作记录。

### 3.7 去重

- 每期开头用一句话交代「上期讲到哪」。
- 同一个能力，只讲「这次新长出来的那一层」。上期讲了 PCF，这期就讲 PCSS 的 blocker search，不要把 PCF 再讲一遍。
- 底稿里标「已写/未写」，不靠记忆。发布后把对应条目的「期号」填上。
- 已发布文章里的记录只读。发现写错了，另起一条「勘误」，写清楚原文哪句不对、改成什么；不要直接改历史。
- 如果这期只是把上期没讲完的讲完，标题里就明说「补上上次没讲完的」。

## 4. 文章结构

### 4.1 标题与头

对外标题固定用这个格式：

```text
重启 RestArtEngine DevLog NN｜<短主题>
```

- 期号两位：01、02。
- 竖线后面用短主题，中英均可：DevLog01 用 `Engine Initialization`，DevLog02 用 `创建可编辑的引擎工作空间`；同一期只选一种。
- 不要只写「开发日志（三）」，也不要写「震惊」「必看」「万字长文」。
- 头里的字段按 1.3 的固定格式，不要每期换顺序。

### 4.2 开头：这一期从哪到哪

200 到 300 字。头里已经有期号、日期、版本、commit，开头不要再重复一遍。

- 直接讲这一期从哪走到哪，一句话结论。
- 读者看完能知道什么。
- 不要讲故事，不要先介绍公司/项目/愿景。

例如：

> 这一版把引擎从「能启动」推到「能编辑」：工程和引擎分开，编辑器能选 Actor、拖变换、改材质，Shader 改完点 Apply 就能看到；前向和延迟共用同一套材质表达。下面先讲这一期怎么和 AI 协作，再按工程、编辑器、渲染、材质四块拆。

协作方法必须单独作为正文第 0 节，具体写法见 4.6。模块内只补充与该模块直接相关的 AI 取舍，不要用一句泛泛的分工说明替代第 0 节。

### 4.3 主体：按系统/模块分节

正文由「协作方法 + 3 到 6 个技术模块 + 验证」组成。协作方法放最前面，按 4.6 写；技术模块按系统或模块分，不按 commit、不按故事。每个技术模块 600 到 1000 字，结构固定，但不要拆成四个小标题：

1. **一段现状 + 改动。** 上一版哪里不够，这一版改了什么，关键决策和给 AI 的约束是什么。不要写成 commit 摘要。
2. **`源码`。** 单独小标题，贴 5 到 20 行真实代码，标文件路径和 commit；前后各用一句话说明看哪里、为什么这样写。
3. **证据。** 截图、公式、命令或数字，至少一种，直接跟在源码/说明后面。截图要说清看哪里、参数是什么。
4. **边界段。** 模块末尾一段，写还没做什么、代价是什么。

只有 `源码` 需要单独标题。不要为了凑结构加「现状」「改动」「证据」「边界」四个小标题。

第 1 期可以按这四个模块拆：工程与启动、编辑器与视口、渲染路径、材质与 Shader。每节只讲一个主题，不要把三个模块塞进一节。

如果这期变化很多，选 3 到 5 个模块写透，剩下的在结尾用一句话带过，不要列一张「这次多了什么」的清单。清单会把文章拉回 changelog。

### 4.4 源码怎么写

源码是文章的主证据，不是装饰。

- 每期至少 2 段源码。全是截图、没有代码，说服力不够。
- 用仓库里的真实代码，不用伪代码。简化过就注明「删了错误处理」。
- 代码从 `include/`、`src/`、`Shaders/` 里取；路径写相对仓库根。
- 一段 5 到 20 行。超过就拆，或者只留关键函数。
- 代码块前写一句「看哪几行」，代码块后写一句「为什么这样写」。
- 标文件路径和 commit：`src/Renderer/SceneRenderer.cpp` @ `cb8fb25`。
- 不要贴整个文件，也不要贴几百行 HLSL。选能说明结构、算法或取舍的片段。
- 代码里的常量、布局、枚举必须和文章里的说法一致；改过就重贴，不要凭记忆写。
- 代码来自公开仓库；如果引用了外部代码，标来源和许可。

### 4.5 结尾（可选）

不要单独写「本期边界与下一期」。每个技术模块的边界写在该模块末尾；整篇最后可以留 1 到 2 句判断，或者直接结束。不要列下期计划。

「综上所述，本期完成了……」是最差的结尾。读者刚看完，不需要你复述。

### 4.6 协作方法：思路、Agents、Skills

这一节不是可选。它对应正文的最前面（第 0 节），不是结尾；规范里放在这里，是因为它要用到前面的源码、截图和验证规则。

每期都要有一节，讲清楚「这期的想法是怎么变成 AI 能执行的任务的」。读者看这个系列，一半是看引擎，一半是看这套协作方法。

先把这套 Codex 配置地图摆出来。文章里不用全贴，但至少要有一张表，让读者知道每一层在哪、干什么：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 模型/provider | `~/.codex/config.toml` | 执行基础设施；具体模型/provider由本机配置管理，不把配置值、凭据或地址复制到文章/角色/技能 |
| 全局规则 | `~/.codex/AGENTS.md` | 跨项目常驻规则；有就写，没有就靠项目规则 |
| 项目规则 | 仓库根 `AGENTS.md` | 目录、命名、验证、红线；每次会话先读 |
| 领域知识 | `docs/`、`README.md` | 按需读：架构、格式、当前边界 |
| 技能 | `.agents/skills/restarengine-devlog/SKILL.md`（项目）或 `~/.codex/skills/<name>/SKILL.md`（全局） | 可复用流程：触发、输入、步骤、验证、输出 |
| 技能接口 | `.../agents/openai.yaml` | 展示名、短描述、默认提示 |
| 命令规则 | `~/.codex/rules/default.rules` | 常用只读命令允许列表，减少重复审批 |
| 任务状态 | `local/docs/ZhihuSeriesLedger.md` | 写到哪、下次从哪开始 |
| 会话 | 当前对话 | 只负责这一轮，不当作长期记忆 |

#### 4.6.1 开发思路路径

不要从「我让 AI 写个引擎」开始。把想法拆成一条可验证的路径：

1. **问题和约束**：这期要解决什么，不能动什么，验收是什么。
2. **拆解**：分成几个能单独验证的小任务，先做哪个。
3. **契约**：先定接口、数据结构、命令和失败行为，再让 AI 写实现。
4. **回路**：实现 → 运行 → 截图/日志 → 人判断 → 下一轮。
5. **固化**：哪些决定要写进 `AGENTS.md`、`docs/` 或 skill，下次不再解释。

文章里要写出这条路径，不要只写「我提示了 AI，它就写出来了」。可以放一张简单的路径图；用 TeX 画成纵向流程更清楚（写法见 6.4）：

```text
想法 → 约束/验收 → 拆解 → 契约 → 实现 → 验证 → 固化
```

#### 4.6.2 怎么把想法喂给 AI

四层上下文，缺一层就容易跑偏：

| 层 | 放在哪 | 作用 |
| --- | --- | --- |
| 常驻规则 | `AGENTS.md` | 每次会话都读：目录、约定、红线、验证命令 |
| 领域知识 | `docs/`、`README.md` | 按需读：架构、格式、当前边界 |
| 本次任务 | 会话里的任务说明 | 目标、非目标、约束、验收、失败样例 |
| 证据 | 代码、截图、日志、命令输出 | 让 AI 看见事实，不靠形容词 |

任务说明按这个模板写：

```text
目标：
非目标：
现状/证据：
约束：
验收：
失败样例：
输出格式：
```

差的任务说明和好的任务说明，差别在这里：

- 差：「帮我优化一下渲染。」
- 好：「目标：把 PCSS 的软边调软，近处保持清晰。非目标：不改阴影分辨率，不动 CSM。现状：`Scene.hlsl` 的 blocker search 采样数是 8。约束：只改采样数和 penumbra 估计，不改常量缓冲布局。验收：同机位对比图 + 帧率不低于 55。失败样例：采样数加到 16 后帧率掉到 48，算失败。输出：改了哪几行、命令、前后帧率、两张截图。」（数字是示例，写文章时换成实测的。）

几条硬规矩：

- 先让 AI 复述计划、风险和要改的文件，再让它动手。
- 一次只改一个可验证点。不要一次给五个目标。
- 给它看真实代码和截图，不要只说「优化一下」。
- 要求它返回文件路径、命令和结果，不接受「已完成」。
- 人保留取舍、命名、边界和发布权。

#### 4.6.3 Agents 配置

本项目实际角色与技能入口以 [AgentDevelopment.md](AgentDevelopment.md) 为准，职责落在三层：

1. `AGENTS.md`：所有角色都遵守的常驻规则。
2. 任务 prompt：这一轮谁负责什么、能改哪些文件、交付什么。
3. `.codex/agents/*.toml`：项目core/rendering/gui角色；技能在 `.agents/skills/`。技能内 `agents/openai.yaml` 仅提供展示/调用元数据，不是项目角色定义。客户端实际加载与兼容读取分别记录。

下面是任务职责拆分示例，不替换项目现有的 core/rendering/gui 领域角色：

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 规划/实现 | 拆任务、改代码、跑验证 | 不给自己签字 |
| 独立审查 | 看冻结字段、版本、测试证据、边界 | 不参与本轮写作/实现 |
| 记录/截图 | 存命令、截图、结果、失败 | 不改技术结论 |

关键不是角色名字，是边界：输入、输出、权限、不做什么，都要写清楚。审查者不能是实现者。

职责表可以再配一张 TeX 单向链：实现 → 审查 → 发布，记录归档。箭头只能单向走，审查者不能回到实现。

文章里至少贴一段真实的角色说明：可以是项目角色 TOML 的职责片段，也可以是任务 prompt 里的「你负责/你不负责」。删掉敏感内容，不要编一个更好看的版本。

#### 4.6.4 Skills 配置

Skill 是「可复用的流程」，不是知识库。本机 Codex 的 skill 结构是：

```text
~/.codex/skills/<name>/
├─ SKILL.md              # front matter: name / description；正文: 触发、步骤、验证、输出
├─ agents/openai.yaml    # 展示名、短描述、默认提示
├─ references/           # 领域资料
└─ scripts/              # 可执行检查
```

项目内也有 `.agents/skills/<name>/SKILL.md` 的用法；结构一样，作用域不同。

本项目的 `restarengine-devlog` 是最小可用例子：`SKILL.md` + `agents/openai.yaml`，正文引用仓库里的规范和底稿，不复制整份手册。本机已有的 `ue-material-agent` 也遵循同一结构；文章只讲结构，不贴 UE 业务细节。

`SKILL.md` 的 front matter 至少写清楚：

```yaml
---
name: <skill-name>
description: <什么时候用；什么时候不要用>
---
```

正文按这个顺序写：触发条件 → 输入 → 步骤 → 验证 → 输出 → 失败处理。能跑的命令放 `scripts/`，领域资料放 `references/`，不要把所有东西塞进一个文件。

什么时候值得写成 skill：

- 同一套流程重复三次以上；
- 有明确的验收命令/截图；
- 换一个会话还能独立跑；
- 失败时知道该回写哪一条。

什么时候不写：

- 一次性任务；
- 没有验证；
- 依赖大量只存在于这次对话里的上下文。

`~/.codex/rules/default.rules` 是另一层：把常用的只读命令加进允许列表，减少重复审批。它不改变角色职责，只降低执行成本。

文章里至少贴一个真实 skill 的 front matter 和目录树，不要贴全文。让读者看到「一个 skill 长什么样」，比列十条原则有用。

#### 4.6.5 这期的协作复盘

每期最后写 3 到 5 条，不要写成感想：

- 哪一步 AI 一次做对，为什么；
- 哪一步需要人重新拆，拆成了什么；
- 哪一步应该写进 `AGENTS.md`、`docs/` 或 skill，下次不再解释；
- 哪一步 AI 帮了倒忙，怎么发现的；
- 下期准备改哪条规则、加哪个 skill。

这一节和模块末尾的「边界」不重复：那里讲引擎没做什么，这里讲协作方法没做好什么。

### 4.7 长度

- 协作方法 500 到 1000 字；技术模块 3 到 6 节，每节 600 到 1000 字。
- 全文 4000 到 7000 字（不含代码块和截图说明）：正常。
- 超过 8000 字：拆两期，或者砍掉一个模块。
- 少于 3000 字：可能阶段没选好，或者证据不够。

字数不是硬指标。但一篇讲引擎进展的文章，如果只有结论没有源码、截图和数字，通常不是「精炼」，是「没写透」。

## 5. 语言：去机器化

### 5.1 十条规则

1. **先写现象，再给名词。**
   「物体边缘有一圈锯齿」比「阴影走的是 2x2 PCF」好懂。先让读者看见，再告诉他这叫啥。

2. **一句话只说一件事。**
   长句拆开。中文句号不贵。

3. **写「改之前/改之后」，不写「优化了」。**
   「优化了加载速度」是结论，「加载从 4 秒降到 1.2 秒」是信息。

4. **数字要落地。**
   分辨率、帧率、采样数、耗时、文件行数、显存占用。给不出数字，就说明还没测。

5. **把边界写透。**
   没做的、没验证的、有限制的，都要写清楚。不用编失败故事，也不要只写成功。

6. **少用排比。**
   「不仅……而且……」「既……又……」用多了像 PPT。一句话能说完就说完。

7. **术语第一次出现，用一句人话垫一下。**
   「CSM（把相机远近分成两段，近处用细的阴影图，远处用粗的）」。

8. **删掉正确的废话。**
   「渲染质量很重要」「性能是关键」——这种句子删了不影响任何信息。

9. **别用「首先/其次/最后」当骨架。**
   用事情本身的顺序：先坏在哪，再试什么，最后变成什么样。

10. **读一遍删 10%，再删形容词。**
    「显著」「大幅」「极致」「非常」——大部分时候删掉更准。

### 5.2 禁词和慎用词

| 词 | 为什么 | 换成什么 |
| --- | --- | --- |
| 赋能 | 没说做了什么 | 直接写「让它能……」 |
| 闭环 | 汇报词 | 「从导入到保存能走通了」 |
| 抓手 | 空洞 | 「先改哪一块」 |
| 沉淀 | 抽象 | 「记下来」「存成文件」 |
| 对齐 | 会议词 | 「改成一样」「确认过」 |
| 颗粒度 | 装腔 | 「细到什么程度」 |
| 范式 | 太大 | 「做法」 |
| 方法论 | 太大 | 「步骤」 |
| 无缝 | 基本做不到 | 「不用重启」 |
| 极致/全面提升 | 不可验证 | 给数字 |
| 值得注意的是 | 废话 | 直接说 |
| 综上所述 | 读者知道要结束了 | 删 |

不是绝对禁止。如果引号里是别人的原话，可以保留。自己写正文时，能换就换。

### 5.3 五组对照

**渲染**

- 差：「通过重构渲染管线，实现了前向与延迟路径的统一，全面提升了材质表现的一致性。」
- 好：「以前改一次材质，要在前向和延迟两套代码里各改一遍。改漏一处，两边颜色就不一样。现在两条路都调用同一个 `ShadeSurface()`，改一处，两边一起变。」

**结构**

- 差：「采用模块化架构，提升了系统的可扩展性。」
- 好：「原来所有东西都堆在入口文件里，改一个面板要翻很久。现在 Scene、Assets、Renderer、Editor 各管各的，编辑器面板只跟 World 和 AssetLibrary 打交道。」

**性能**

- 差：「性能显著提升。」
- 好：「同一个场景，1600×960，阴影从 2x2 PCF 换成 PCSS，帧率从 61 掉到 48。把采样数从 16 降到 8，回到 55，软边也还能看。」（数字要换成你实测的。）

**AI 协作**

- 差：「AI 大幅提升了开发效率。」
- 好：「阴影切换的枚举和分支由 AI 起草；评审时删掉了重复的 60 行，把模式选择收进一个 `switch`。AI 写得快，但保留哪些分支是人判断的。」

**开头**

- 差：「随着实时渲染技术的发展，越来越多的开发者开始关注引擎架构。」
- 好：「这一期处理的是阴影切换：9 种方案共用一张 2048² 深度图，切换只改一个枚举。下面先给资源布局，再给 PCSS 的采样代码和两张同机位对比图。」

这些例子里的人、时间、数字都是占位的。写的时候换成真实发生的。

### 5.4 AI 味自检

写完一段，问自己八个问题：

1. 第一段删掉，文章还能读吗？能，就删。
2. 有没有一句话放在任何项目都成立？有，就删。
3. 有没有具体的时间、数字、文件名、命令？没有，就补。
4. 有没有一段是「首先/其次/最后」？有，换顺序。
5. 形容词是不是比动词多？是，删形容词。
6. 有没有在解释「这很重要」，而不是「这怎么做」？有，改成做法。
7. 读起来像不像产品介绍？像，改成同事复盘。
8. 有没有一句是你自己真的想说的？没有，这段可能不该写。

### 5.5 语气

- 用「我们」可以，但别每段都「我们认为」。
- 可以写判断失误，但重点放在怎么发现、怎么改，不写心路历程。
- 语气可以放松，但不要玩梗。读者是来看技术的。
- 不教育读者，不喊口号。「让我们一起见证」这种话，删。

## 6. 证据：截图和公式

源码规则见 4.4。这一节管截图和公式。

### 6.1 三类截图

建议覆盖三类：

1. **全景**：这个东西长什么样。编辑器全貌、场景全景、工程目录。
2. **对比**：之前/之后。同机位、同参数，两张并排。
3. **细节**：一个参数、一条边、一个面板。让读者看清差别。

有条件时覆盖全景、对比、细节三类；纯工程或架构阶段可以用命令、源码、日志或公式替代缺失的画面。DevLog02 的工作区、实例 Details、材质反馈等可视交互内容必须配真实运行画面，不能用 PASS 日志替代这些画面。没有证据的行为保留待拍状态或删去相应完成宣称。不要用示意图冒充运行截图。

### 6.2 图注

图注写「看哪里、差多少」，不写「如图所示」。

- 差：「如图所示，阴影效果更好了。」
- 好：「左：2x2 PCF，边缘是硬的。右：PCSS，同样的光源，边缘按距离变虚。两张都是 1600×960，曝光 1.0，提交 `cb8fb25`。」

本地 Markdown 用 `![图注](YYYY-MM-DD_第NN期_assets/01-overview.png)`。知乎发布时上传图片，图注单独写一行，不要只依赖 alt 文本。

### 6.3 截图规矩

- 用真实运行截图，不用 AI 生成或重绘界面。允许裁剪、隐私遮挡和标注，原图保留；并排对比只排列真实同条件图片，标明两个状态，不伪造单一运行画面。功能没跑通就不放图。
- 截图来源写清楚：`--editor-self-test --capture-dir artifacts\editor-validation`、`Validate-Render.ps1` 生成的，还是 F9 手动截的；命令和目录记在底稿里。
- 同一组比较固定窗口、DPI、镜头、曝光和渲染参数。DevLog01 的原始运行基准为 1440×900，发布图有 1440×860／1440×585 的裁剪；DevLog02 优先沿用 1440×900，或为实际工具窗选择可读尺寸，不机械扩大。记录原始和导出尺寸，不把裁剪图标成原始分辨率。
- 固定相机、曝光、渲染路径。对比图必须同机位。
- 关掉无关面板，别让读者在截图里找重点。
- 角落标上版本/commit，方便以后对照。
- 需要指出的地方，加箭头或框；不要只写「注意这里」。
- 不要在截图里露出 token、内网地址、用户名、绝对路径。

### 6.4 TeX 公式

知乎支持 TeX，能用就用，但别为了显得专业硬塞。

适合用公式的地方：

- 光照/材质：GGX、Schlick Fresnel、ACES 近似。
- 阴影：PCSS 的 blocker search、penumbra 估计、PCF 权重。
- 光追：射线与球、平面、三角形求交。
- 矩阵/向量：世界、局部、裁剪空间的变换。
- 分段函数：模式切换、权重混合、阴影选择。
- 性能：采样数、分辨率、耗时的关系。

写法：

- 行内用 `$...$`，独立公式用 `$$...$$`，以知乎当前编辑器实际支持为准。
- 一个公式配一句人话：在算什么，哪个符号对应代码里的哪个变量。
- 符号表只列文章里出现的，不要抄教科书。
- 中文尽量放在公式外面。公式里用 `\text{}` 时先在知乎预览，部分端会渲染失败。
- 流程图用 `\begin{array}` + `\boxed{\text{...}}` + `\xrightarrow` / `\downarrow`；不要用 TikZ，知乎的 MathJax 不执行它。
- 图里的中文放在 `\text{}` 里，标签尽量短。中文渲染失败就换英文缩写，或者退回截图。
- 一篇文章 2 到 5 个公式足够。每个公式要能对应到代码或截图，不是装饰。简单加减乘除不用 TeX。
- 发布前在知乎编辑器里预览，手机也看一遍；渲染失败就退回文字或截图。

示例：

> 高光项用 GGX 的法线分布：
>
> $$D(h)=\frac{\alpha^2}{\pi\left((n\cdot h)^2(\alpha^2-1)+1\right)^2}$$
>
> 其中 $\alpha$ 是代码里的粗糙度参数，$n$ 是法线，$h$ 是半程向量；具体取值以 `Standard.hlsli` 的实现为准。

### 6.5 可复现

每期至少给一个读者能照做的小实验：三条以内的步骤，给参数。

比如：

1. 打开 Sandbox 工程。
2. 按 F2 切到 Deferred，Viewport 里把 Shadow method 改成 PCSS。
3. 把 Key light 的强度从 5 调到 8，看软边的变化。

不用长，但要能复现。读者跟着做一遍，比看你十张图有用。

### 6.6 DevLog02 媒体制作与落位

沿用实际 DevLog01 的方式：编号图片放在本期 `_assets`，正文在解释相关行为的段落附近嵌入相对链接，图注交代目标、参数和观察点。第 1 期现存正文引用 10 张编号 PNG；同目录另有一张 Snipaste PNG 和一段 880×652、41 帧、4.2 秒、627,504 字节的 GIF，后两者未被现存 Markdown 引用。不能把“文件在目录里”写成“正文已经使用”。既有正文、配图和头图不因准备下一期而覆盖。

**位置分三层，先列拍摄清单再写正文：**

1. 原始证据：隔离工程运行的原图、录屏、日志留在独立证据目录；可使用被忽略的 `artifacts/<任务>/`，不写入用户工程 Content，不参与 GC。静态最终帧不能证明连续拖动中的反馈。
2. 发布素材：外部栏目根的 `YYYY-MM-DD_第02期_assets/`，最终 PNG 与 GIF 都在该目录，文件名如 `01-workspace.png`、`02-dock-reflow.gif`；原始 MP4／大序列和诊断日志不作为发布图混入。日期沿用最终正文日期，改名时同步引用。根目录 `head.png`／`head.psd`、`title.png`／`title.psd` 是既有系列资源，不擅自更换。
3. 正文位置：紧跟讲解该现象的段落或源码之后，图注随后说明看哪里；不把全部截图堆在结尾。示例为 `![图2：拖离面板后视口随可用区域重排](YYYY-MM-DD_第02期_assets/02-dock-reflow.gif)`。同一功能的前后对比相邻放置，顺序和图注一致。知乎上传时另写可见图注。

本机绝对输出根只取 `local/machine/Paths.md`；确认 `head.png`、`head.psd` 存在后使用。DevLog02 逐图动作／来源／落位表由 `ZhihuSeriesLedger.md` 维护。画面来源要区分：F9／Capture 是场景／主窗口输出；独立材质窗口需平台窗口渲染目标或实际桌面捕获；原生另存为对话框及非客户区覆绘必须用实际桌面画面，不能拿 backbuffer 截图证明它们正确。

**GIF 的本系列硬限制：每个最终文件 ≤ 5,000,000 字节。** 这是用户约定，采用十进制 MB，不能用 PowerShell 的 `5MB`（5,242,880 字节）放宽，也不宣称这是知乎官方当前上限。

- 只在时间过程能解释问题时使用 GIF，例如停靠重排、Alt 复制后撤销、按住材质滑块时的实时反馈；其余用清晰 PNG。无需强行给每个模块做动图。
- 从真实连续录屏制作：保留动作前状态、按下／拖动、结果与必要撤销／丢弃步骤；不能把无关测试截图拼成“实时操作”，不用生成帧或插值伪造反馈。帧序列没有可靠时间信息时，只能标作离散状态演示，不能称连续实时录屏。
- 建议先取 3–6 秒、10–12 fps、宽 800–960 px 的相关区域，优先裁掉无关桌面并缩短停顿，再调整帧率／尺寸／调色板。它们是起步参数，不是硬阈值；小字、数值和光标必须可读。
- 保留原始录屏。使用调色板生成／复用优化颜色，Two-sided／法线／色彩精确对比优先用 PNG；不能为了体积把关键视觉差异压没。压缩后重新测量实际文件字节数，超过上限继续调整或改用静态对比并准确说明，不直接交付超限文件。
- 需要循环演示时保留可读的首尾停顿；完整播放检查跳帧、闪烁、残影、循环接缝、鼠标和参数变化。裁剪／遮挡必须逐帧覆盖私人目录、用户名、通知和本机路径；不能只检查首帧。加速／变速要在图注说明，不拿变速 GIF 证明实际延迟或性能。

**验收记录：** 每张最终媒体登记原始来源、对应 commit／构建、捕获方式、隔离工程、原始／输出尺寸、帧数／时长／帧率（适用时）、编码后字节数、正文段落、图注、隐私与目视检查结果。已有历史证据只是候选，未采集／未压缩／未检查均标待完成，不用“已归档”代替实际文件和引用。

本机检查入口（Python 3＋Pillow，从仓库根运行，文件名换成实际正文）：

```powershell
uv run --offline python .agents/skills/restarengine-devlog/scripts/validate_media.py --article '<外部栏目根>/YYYY-MM-DD_第02期_短标题.md' --report artifacts/devlog02-media-check.json
```

脚本检查相对引用、本期目录归属、文件存在与解码、尺寸、GIF 帧数／时长和 5,000,000 字节上限，也报告目录中未被正文引用的图片；不会修改媒体。退出码 0 只表示文件检查通过，不能代替目视隐私检查、GIF 完整播放、正文落位或知乎手机预览。仅修规范／准备素材时可用 DevLog01 现存文件与隔离测试文件验证检查器，不把测试夹具当作 DevLog02 成品。

## 7. 平台适配

知乎的编辑器对 Markdown 支持有限，表格和代码块容易变形。先在本地用 Markdown 写，发布前转一遍。

- 标题控制在 30 字内，手机上一行能显示完。
- 标题层级按知乎排版：主章节用一级标题，子节用二级标题。正文 Markdown 里就是 `##` → `#`、`###` → `##`；期号/模块/验证是一级，`源码` 和 0.1-0.5 是二级。
- 开头三行内出现本期范围和结论，不要从行业趋势写起。
- 每 600 到 800 字一个小标题，手机上不会一屏全是字。
- 表格尽量改成短段落或列表；必须保留的表格，发布后检查有没有错位。
- 代码块在知乎容易变形；变形就改成截图或纯文本，不要硬贴。
- TeX 公式发布前在知乎编辑器里预览；`$$` 不渲染就换行内写法或截图。
- 图片宽度保持阅读一致性；GIF 按第 6.6 节制作，每个最终文件不超过 5,000,000 字节，测量后完整播放验收。
- 外链放文末，正文里写「文末链接」。知乎对外链不友好，读者也懒得点。
- 发布前用手机看一遍。很多排版问题，手机上才看得见。

## 9. 和 Codex 的接口

### 9.1 为什么这样放

Codex 的结构不复杂：它每次会话先读 `AGENTS.md`，然后按需要读仓库里的文件。模型是插进来的，今天用 DeepSeek，明天换别的，读文件的顺序不变。

所以规范不能写成「请记住」，要写成「先读哪个文件、按什么顺序做、做完改哪个文件」。

这也是为什么文件这样分工：

```text
AGENTS.md                     公开轻量入口，保持在RAEngine根使用
local/docs/AgentEntry.md       协作触发规则、红线与文件指针
local/machine/Paths.md         本机输出根，两个Git仓库均忽略
.agents/skills/restarengine-devlog/SKILL.md
                              Codex 可复用执行流程；触发后先读，再按本规范取证和写作
local/docs/ZhihuSeries.md           怎么写，长，写的时候读
local/docs/ZhihuSeriesLedger.md     写作底稿，拆正文前用，不发布
<输出根>/YYYY-MM-DD_...md     正文，按日期命名，每期一篇
```

把它们都塞进 `AGENTS.md`，会话一开始就背着几千字，后面真正干活的空间就少了。只放在聊天里，下次会话又找不到。文件分工解决的是「记得住」和「装得下」。但底稿不是另一个发布物：它只在下笔前用，写完就融进正文。

### 9.2 文件职责

| 文件 | 角色 | 谁改 | 什么时候改 |
| --- | --- | --- | --- |
| `AGENTS.md` | 公开通用入口、协作库调用指针 | 人 | 调用方式变化时改 |
| `local/docs/AgentEntry.md` | 协作触发器、红线、文件指针 | 人 | 工作流变化时改 |
| `local/machine/Paths.md` | 本机文章输出根 | 人 | 换机器后确认并配置，不提交 |
| `.agents/skills/restarengine-devlog/SKILL.md` | Codex 可复用执行流程，引用本规范和底稿 | 人 | 工作流或边界变了 |
| `local/docs/ZhihuSeries.md` | 写作规范 | 人 | 规范变了才改 |
| `local/docs/ZhihuSeriesLedger.md` | 写作底稿（不发布） | 人或 AI | 每次写作前、发布后 |
| `<输出根>/YYYY-MM-DD_第NN期_短标题.md` | 正文 | 人或 AI | 每期 |

输出根是机器相关配置，只写在忽略的 `local/machine/Paths.md`，不写进会提交的入口或 docs。

公开 `AGENTS.md` 只放通用调用指针；协作 `AgentEntry.md` 也不复制写作规范全文，避免多处漂移。

### 9.3 Codex 执行契约

下面这段是执行契约的正文参考。项目实际技能入口是 `.agents/skills/restarengine-devlog/SKILL.md`；公开 `AGENTS.md` 指向协作 `AgentEntry.md`，后者保留触发词、文件指针和红线；机器输出根独立放 machine/Paths.md，避免契约漂移。如果只能留三条，留第 1、4、7 条。

```markdown
## 知乎连载

触发词：写知乎、下一期、阶段总结、把这阶段写成分享。

1. 先读 `AGENTS.md`、`local/docs/AgentEntry.md`、`local/docs/ZhihuSeries.md` 和 `local/docs/ZhihuSeriesLedger.md`；从 `local/machine/Paths.md` 拿输出根。这期用到 skill 时，读对应 `SKILL.md` 和 `agents/openai.yaml`。换机器时先向图灵老师确认，不要沿用旧路径。
2. 列出输出根里 `^\d{4}-\d{2}-\d{2}.*\.md$` 的文件，按日期倒序。最新一篇是「上次」；一篇都没有就是第 1 期；最新日期等于今天时，先问是改这篇还是新写一篇，不要覆盖。
3. 确定起点：上一期文章开头写的终点 commit 优先（底稿里也有）；没有就用上一期文章日期跑 `git log -1 --before="<日期> 23:59:59"`；第 1 期用 `git rev-list --max-parents=0 HEAD`，收集时加 `--root`，否则漏掉初始提交。终点用发布时最后一个引擎提交，写作/底稿提交不算。
4. 用 `git log --oneline <起点>..HEAD`、`git diff --stat <起点>..HEAD`、`git diff <起点>..HEAD -- README.md docs/` 收集变化；第 1 期改用 `git log --oneline --root HEAD`，避免漏掉初始提交。有未提交修改时先 `git status --short`。
5. 把变化按 结构/思路/渲染/操作/工程/稳定/修复/边界 归类，作为新条目写进底稿，并标正文落点；已发布期的记录只读。每条标 A/B/C 证据等级。
6. 收集协作方法：这期的任务说明、用了哪些 `AGENTS.md`/`docs/`/skills/agents、哪一轮返工、准备固化什么；写进正文第 0 节，不要写成通用教程。至少贴一段真实配置（`AGENTS.md` 片段、`SKILL.md` front matter 或 `agents/openai.yaml`）。
7. 先拆底稿，再写正文。底稿的每条内容要变成正文里的小节或段落，不要贴成清单；每个技术模块至少一个证据（源码/截图/公式/命令）。边界写在该模块末尾，不要另起「本期边界与下一期」一节。
8. 正文写到输出根，文件名 `YYYY-MM-DD_第NN期_短标题.md`；配图放 `YYYY-MM-DD_第NN期_assets/`。
9. 正文/配图不提交：本地副本放 `.zhihu/` 或带 `.zhihu` 标签；提交前跑 `git status` 和 `git ls-files | Select-String 'zhihu|知乎|DevLog|\.zhihu'`，不要 `git add -f`。
10. 发布前检查：禁用词、空话、重复、夸大、密钥/内网地址/本机绝对路径。
11. 发布后：实际日期变了就改名；回填底稿和正文开头的范围（期号、链接、日期、终点 commit）；打 tag `DevLogNN`。
12. 不要编造功能；不要把计划写成已完成；不要把上一期讲过的再讲一遍。
```

内部交付要求：更新后的底稿 + 正文 Markdown + 证据索引 + 自检结果。底稿、证据索引和自检是工作元数据，不是第二篇发布物；少一样都算这次写作流程没完成。

第一次用，可以直接这样下指令：

> 读 `local/docs/ZhihuSeries.md` 和 `local/docs/ZhihuSeriesLedger.md`。先确认本机输出根和最新一篇的日期，再把这阶段的变化按八类填进底稿，标好 A/B/C 和正文落点。先别写正文，最后告诉我第 1 期适合讲哪几个模块，以及「这期是怎么和 AI 一起做的」准备怎么写。

先让它交底稿和正文落点，再写正文。顺序反过来，它就会先编结构，再找证据。

### 9.4 Codex 与 DeepSeek（补充模型）的同步

1. 按 [WorkspaceSync.md](WorkspaceSync.md) 分别拉取引擎与 `local/` 协作库；先处理运行副本修改，再 Install。仍从 RAEngine 根使用 `.agents/skills/restarengine-devlog/`，不改工作目录、不从镜像执行。
2. 根 `AGENTS.md` 指向协作 `AgentEntry.md`；两个模型共读本规范、底稿及 DevelopmentStatus，不各建一套副本。当前机器文章路径单独确认并填入忽略的 `local/machine/Paths.md`。
3. 新会话按本期真实任务启动，先检查输出根、最新文章、底稿、上一期正文及引擎基线；不把协作库 commit 当成引擎功能 commit，也不把历史截图当成本轮验证。
4. 写作完成后规范与底稿直接保存在协作库 docs；修改了技能则 Collect 收集，分别审查两个仓库的 diff。正式稿与配图仍在外部目录，不随协作库同步。
5. 无法读取协作库、路径或证据时说明具体缺失，不能直接编写“已完成”。每条变化要有真实源码、命令或画面证据。

这套规范不依赖某个模型。DeepSeek、GPT、Claude 都按同一套文件读。换模型无需复制进度或改规范；模型服务设置由工具自身管理，本同步流程不读取或更改它。

### 9.5 常见失效

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 直接开写，没读底稿 | 触发词没绑文件 | 在 `AGENTS.md` 里写死「第一步读底稿和上一期文章」 |
| 重复上一期 | 底稿没标已写 | 每次先读「已写内容」 |
| 把计划写成已完成 | 没有证据等级 | 强制 A/B/C，C 只能进「下一步」 |
| 文风像 AI | 规范太抽象 | 用 5.3 的对照例，别用形容词 |
| 泄露密钥/内网地址 | 没有隐私检查 | 发布清单加一项，截图打码 |
| 文章像流水账 | 按 commit 顺序写 | 按系统/模块分节，每节五段 |
| 只有结果，没有协作方法 | 只收集了功能变化 | 要求写第 0 节：思路路径、怎么喂、agents/skills、复盘 |
| 协作方法像通用教程 | 没写本期实际用了什么 | 要求点名本期用的 `AGENTS.md`/skill/角色/返工 |
| 写错文件夹 | 换机器没确认同步盘根 | 先问图灵老师；确认目录里有 `head.png` 和 `head.psd` |
| 覆盖今天已有的文章 | 没检查今天日期 | 先列文件；日期等于今天时问「改还是新写」 |
| 日期和 commit 对不上 | 用日期猜了起点 | 以上一期文章开头写的终点 commit 为准，并记下差异原因 |

### 9.6 规范本身的版本

- 每改一次规范，底部「变更记录」加一行，版本号加 0.1。
- 改结构、改流程、改底线，升一个大版本，比如 v1.x → v2.0。
- 底稿记「规范版本」，不跟规范同号。底稿可以一直用，规范可以换版本。
