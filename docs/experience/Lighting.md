# 场景灯光与多路径一致性

## 场景与原因

将固定方向光／环境扩展为 Light Actor 时，只修改像素着色器或增加编辑器字段不够：资产依赖、几何统计、拾取、GI历史与旧矩形采样都依赖原有单网格Actor假设。旧矩形与新列表如果同时消费会重复计光，最后一个灯隐藏后若按可见灯数选择fallback会意外恢复默认太阳。

## 做法

- 来源接管依据场景是否包含灯光Actor，不能依据可见灯数；隐藏最后灯仍使用显式灯光，删除所有灯才恢复旧来源。
- 灯光与mesh互斥，序列化/保存依赖/资产删除扫描/几何统计/拾取/DXR几何都显式分支。光源参数进入独立常量和GI历史键，不进入几何加速结构重建签名。
- CPU/HLSL共享有界光源表，buffer大小/offset/member反射一起校验；Sky另行累加，超预算保留数据并显示原因。
- PathTracing的矩形面积与BRDF采样使用配对MIS；旧b5区域灯与新b7列表入口互斥，路径积分跳过普通四点矩形积分，避免同灯被累计两次。
- 区分硬件预览、Progressive完整成图与Realtime间接输出。硬件GI开启不自动意味着主光栅局部直接光阴影来自DXR，界面必须说明实际支持模式。

## 验证与边界

逐灯GPU normal/albedo选择真实接收面，剔除遮挡体自身和轮廓，再比较强度/颜色/朝向/范围/投影开关；有限阴影同时测试灯前与灯后遮挡。Forward/Deferred比较相同mask，硬件证据必须包含真实dispatch。GI参数变化检查历史revision及自动重置第一帧与显式清空后的GPU图像一致。

仅CPU数据相等不能证明像素路径；单灯不能覆盖矩形多源MIS；灯光数据平台无关不等于其他后端已可用。

来源：[灯光任务](../tasks/2026-10-29-lighting/README.md)，16项CPU、扩展灯光GPU84dispatch和GI1291dispatch均通过；完整GUI首轮Outliner被新增创建行挤压，v3改为同一创建行/窄矮菜单并保留最小列表后通过完整GUI，两主题已检查。Actor Rect与legacy MIS能量对照及红蓝双灯线性叠加实际GPU通过。原始证据位于artifacts/lighting/，未同步时不能冒充本机复测。

## 混合工作区提交与集成验收

多个任务共享文件时，从已提交基线构造候选树，并使用 alternate index 提交精确增量；验证对象必须是该树，不用混合工作区的通过结果替代。准备期间 HEAD 变化时，先做三方合并并复核受影响接口，避免以旧整文件覆盖已提交功能。资产删除的保存场景引用扫描也属于新组件格式兼容范围，灯光 Actor 不应虚构 mesh 引用，混合组件仍应拒绝。

跨卷复制测试项目后，旧工程绑定恢复可能因无法生成相对 engineRoot 而删去路径，再经本机注册表加载另一套 Shader。常量尺寸不匹配时先核实实际引擎绑定与源码，不放松反射契约。本次通过同卷隔离目录验证候选，未改变用户注册表；跨卷绑定能力本身需另行修复。

Save Scene 测试先由 World 写 fixture 时，编辑器保存前再改一个字段，重开后核对新值，防止保存失败仍凭旧 fixture 通过。灯光与浮窗同时存在时，标记优先命中与桌面坐标映射都需保留，测试先恢复浮窗布局再执行灯光控件操作。来源：[v4 提交验收](../tasks/2026-10-29-lighting/v4.md)。
